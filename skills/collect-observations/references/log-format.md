# Log format

Read before writing a log comment or the log body. The log is one issue: its comments hold copies of the PRs' observations comments, and its body holds a status table with one row per item, where decisions are recorded. The markers below are how a later run tells what is already collected, so never drop or change them.

`triage-observations` reads the log's markers, status table and status values. Check that skill when changing any of them so it can still read the log.

## Markers

| Marker | Where | Meaning |
|---|---|---|
| `<!-- orchestrate-issue:observations -->` | A PR comment, posted by `orchestrate-issue` | The PR's observations comment, the source |
| `<!-- collect-observations:log -->` | The last line of the log body | This issue is a log |
| `<!-- collect-observations:source pr=<PR> comment=<comment id> -->` | A log comment, one line per copied source | That source comment is collected here |

`<comment id>` is the source comment's numeric `id` from `scan.sh`, not its URL.

## Log comment

One log comment holds one or more PRs, in ascending PR order. For each PR, copy its observations comment:

- Keep the source's groups (`### PR #<PR> (issue #<issue>) — at <SHA>`) and items exactly as they are: the item IDs, paths, SHAs and wording. The log is a record of what the agents reported; a reworded item could change its meaning.
- Remove the source's signature block (the `---` line, the `<sub>Generated by ...</sub>` line and the `<!-- agent-signature ... -->` line) and its `<!-- orchestrate-issue:observations -->` marker. The marker would make the log comment look like a PR's observations comment.
- Keep the incomplete-history line (`Observations from earlier sessions on this PR are not included.`) if the source has one, right under that PR's first heading, so the log shows the PR's history is incomplete.
- Under the PR's last group, add a line linking the source comment: `Copied from <source comment URL>`.
- A source with no items (`No observations were reported in this session for PR #<PR> (issue #<issue>).`) becomes a heading and that line, so the log records "none" rather than leaving the PR out:

```markdown
### PR #<PR> (issue #<issue>)

No observations were reported in this session for PR #<PR> (issue #<issue>).

Copied from <source comment URL>
```

End the comment with a blank line, the signature, and one source marker per copied source ("Posting a log comment" in `github-commands.md`):

```markdown
### PR #40 (issue #39) — at 1a2b3c4

**#40-1** — `src/a.ts:12`
- Observation: ...
- Not raised because: ...
- Related: ...
- Source: reviewer

Copied from https://github.com/OWNER/REPO/pull/40#issuecomment-111

### PR #41 (issue #39)

No observations were reported in this session for PR #41 (issue #39).

Copied from https://github.com/OWNER/REPO/pull/41#issuecomment-222

---
<sub>Generated by ...</sub>
<!-- agent-signature v=1 ... -->
<!-- collect-observations:source pr=40 comment=111 -->
<!-- collect-observations:source pr=41 comment=222 -->
```

The heading `### PR #<PR>` mentions the PR, so GitHub adds a cross-reference to the PR's timeline. That cross-reference is how `scan.sh` finds this log from the PR, so keep the plain `#<PR>` reference in the heading.

Keep each comment under 60,000 characters (`wc -m`), below GitHub's 65,536 limit with room for the signature and markers. Start a new comment when the next PR would not fit. Never split one PR's source across comments: its source marker must be in the comment that holds all of its items.

## Log body

A new log uses `assets/log-template.md`:

- Title: `<area>: <scope> review observations log` (e.g. `docs: M1 review observations log`), with the area as the repository's existing issues name it.
- Replace `<scope>` and `<when the log closes>` with the scope the user gave (a milestone, a parent issue, a list of PRs).
- Keep the section headings in English, like `create-issue`. The prose follows "Language" in SKILL.md.
- Labels: an existing documentation label (e.g. `documentation`) if the repository has one. Do not create labels.
- Milestone: the milestone, when the scope is one. Parent: the parent issue, when the scope is its sub-issues; end the body with `Part of #<parent>.` and drop that line otherwise.
- Leave out the **PRs with no observations** line when no copied source is a no-observations one.
- The last line is `<!-- collect-observations:log -->`.

When appending to an existing log, change only:

- The status table: add the new rows after the existing ones. Do not change, reorder or delete existing rows; their statuses are decisions people made.
- The **PRs with no observations** line: add the new PRs (add the line after the status values line if it is missing). See "PRs with no observations" below for which PRs go there.
- The log marker: add `<!-- collect-observations:log -->` as the last line if the body does not have it (a log written before this skill). The plan says so first.

## Status rows

One row per item, in the order of the log comments:

| Column | Content |
|---|---|
| Item | `[#<PR>-<n>](<log comment URL>)`, linking the log comment that holds the item |
| Summary | A short phrase (about 60 characters) saying what the Observation is about. Describe it; do not judge it |
| Status | `open` |

Never set a status other than `open`, and never write a reason in the Summary. Deciding each item (an issue, folding it into one, dropping it) is the user's step after this skill.

An ID already in the table is not added again.

If the body would exceed 65,536 characters, do not cut rows. Stop and tell the user, who can start a next log and move the open items to it.

## PRs with no observations

The line lists only PRs whose copied source is the no-observations line (`No observations were reported in this session for PR #<PR> ...`): a recorded "none". `orchestrate-issue` posts that line so a log can tell "none" from "forgotten".

Never list a `no-comment` or `not-merged` PR there. Nothing was recorded for them, so listing them would turn "forgotten" into "none". They appear only in the plan and the final report.

## Leftovers

A run that posted log comments and then failed to update the body leaves items in the comments with no row. The next run usually scans the same PRs, finds them `collected`, and would have nothing to post, so check every log the run reads (the `--log` issue and the logs under `collected`):

- An item ID in a comment with a source marker but not in the status table: add its row.
- A PR whose copied source is the no-observations line but not on the **PRs with no observations** line: add it.

List these in the plan as repairs. They are written in step 6 even when no comment is posted.
